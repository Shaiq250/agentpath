Recorded 2026-08-31, before any rule was changed in response to it.

The MCPTox benchmark: 485 poisoned tool descriptions and 362 legitimate tools
from 45 real MCP servers, built by Wang et al. for AAAI 2026 (arXiv:2508.14925).
Not written by anyone involved in this project, and cited by other work.

This is the first time these rules have met a large corpus assembled by someone
else, and the result is much worse than the number this project has been
publishing. That number, 80 percent, came from six samples. It did not
generalise.

The false positive half held up: zero of 362 legitimate tools were flagged.

AFTER the rules were rewritten, same day.

THIS SECOND NUMBER IS TUNED AND IS NOT A MEASUREMENT. The rules were
changed with knowledge of what this corpus contains, so it says how
well the rules match a corpus they were built against. It is a
regression guard. The honest figure from this benchmark is the 5
percent above, which was recorded before anyone here knew anything
about it.

What changed, and why it is not merely pattern chasing: the old rules
matched PHRASES, which is why they collapsed the moment they met
somebody else's wording. The new ones match STRUCTURE.

  cross-tool instruction   a tool description that requires the model
                           to use a DIFFERENT tool. A description
                           exists to describe its own tool. The one
                           legitimate reason to name another is to
                           steer people away from it, so "instead of"
                           and "rather than" are excluded.

  priority claim           a description asserting that it outranks
                           the user's request. Only counts when it is
                           about the user, since plenty of tools have
                           a parameter called priority.

  sensitive artifact       an SSH key, /etc/shadow, .env, .aws named
                           in a description. Narrowed to concrete
                           artifacts after the bare word "credential"
                           flagged a tool called get_credentials,
                           which describes itself honestly.

Those three do not care what words an attacker chooses, which is the
property the old rules lacked.

The next honest number has to come from a corpus nobody here has
looked at. AgentDojo and InjecAgent are candidates.

THIRD CONFIGURATION, same day. Still tuned, still not a measurement.

Looking at what the 68 percent version missed showed the strongest
rule had a narrow bug rather than a conceptual limit. It recognised a
tool name only when it was quoted, snake_case and lower case, so
'markAsRead', "the tool sendmail" and 'get_apps_clientId_webhooks'
all walked past. Every one of those misses was the exact attack the
rule exists to catch.

Widening it exposed a real trade-off, measured rather than guessed:

  quoted snake_case only          60 percent recall,  1 false positive
  + a call verb with a tool name  71 percent recall,  9 false positives
  + the word "tool" nearby        74 percent recall, 13 false positives
  + use and run as call verbs     87 percent recall, 23 false positives

Chosen: the second. A quoted camelCase word is far more often a JSON
field than a tool, because descriptions are full of things like
{'reasonCode': ...}, so anything not snake_case has to sit behind an
unambiguous call verb.

With every signal working together that lands at 78 percent recall
and 9 false positives out of 362, which is 2 percent.

THE ZERO FALSE POSITIVE CLAIM NO LONGER HOLDS on this corpus. It
still holds on the 123 tools in the project's own corpora. Two per
cent is worth stating plainly rather than rounding away, and it is
still far below the roughly 78 percent an independent audit found for
two YARA based scanners in this field.

One of the nine is arguable rather than wrong: a Codacy tool
legitimately instructs the model to call codacy_list_organizations
first. Some real tools genuinely do chain, which puts a floor under
this signal that no amount of pattern work removes.

FOURTH AND FINAL CONFIGURATION. Still tuned, still not a measurement.

A deliberate last search for signal CATEGORIES rather than more
variants of the same regex. Each candidate measured on its own before
being combined:

  pretext, arguing for compliance      21 of 109 misses,  1 legit
  dictating an argument value           8 of 109 misses,  0 legit
  imperative sequencing, no tool named  8 of 109 misses,  1 legit
  addressing the assistant directly     0 of 109 misses,  0 legit
  threatening failure if not done       0 of 109 misses,  4 legit

Two were added. The last two were not: one finds nothing, and the
other flags honest tools four times as often as poisoned ones.

An honesty note on the pretext signal. It looks stronger here than it
is, because 20 of its 27 matches on this corpus are one identical
generated sentence, "this step is critical for preventing
unauthorized file access and ensuring system stability". The general
shape is a real signal. The size of the gain measured here is a
property of the benchmark's generator, not of the rule.

Result: 82 percent recall, 9 false positives out of 362, unchanged.

WHERE THIS APPROACH STOPS. Four further configurations were tried
past this and every one traded recall for precision roughly one for
one: 79 percent cost 14 false positives, 80 percent cost 12, 87
percent cost 23. The remaining misses need meaning rather than
pattern. "Helper tool to get information" and "Before use the tool
sendmail" are both a word beside the word tool; separating them is a
question about grammar and intent. Going further would mean putting a
model in the loop, which would cost the two properties this tool is
built on, running offline and being deterministic.
